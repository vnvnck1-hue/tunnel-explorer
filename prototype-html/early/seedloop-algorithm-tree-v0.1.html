PC + 크롬 확장

기기 브리지 · 조건부
  • 남의 게임을 실제로 띄워서 플레이
  • 스크린샷 촬영 → 아트 관찰
  • PC가 켜져 있고 데스크톱 앱이 떠 있어야 한다
  • 꺼지면 그날 밤엔 못 쓴다
이 분담은 취향이 아니라 물리적 제약이다. 그래서 루프는 “찾고·분석하고·만드는” 무인 레인과 “실제로 만져보는” 조건부 레인으로 쪼개지고, 둘은 기억(GitHub)으로만 이어진다. PC가 죽어도 밤 작업은 실패하지 않고, 검증만 다음으로 미뤄진다.

하룻밤 1사이클 · 판정 트리

STAGE 0

기억 복구

새벽에 깨어난 세션은 형님과의 대화를 하나도 기억하지 못한다. 초면이다. 그래서 첫 동작은 무조건 기억 불러오기다.

# 판단 기준과 지금까지의 이력을 끌어온다 git clone <seedloop repo> read runbook/nightly.md ← 오늘 밤 실행 순서 read runbook/rubric.md ← 점수표와 가중치 read registry/seen.jsonl ← 이미 본 게임 전부
이 단계가 없으면 루프가 아니라 매일 처음부터 다시 시작하는 단발 작업이 된다. 어제 기각한 게임을 오늘 또 발굴하고, 어제 배운 걸 오늘 못 쓴다.
CHECK

repo 접근이 되는가?

git 프록시가 자격증명을 끼워주는 저장소 목록에 이 repo가 등록돼 있어야 한다.

YES

정상 진행 — 툴체인까지 확보. 프로토타입 제작 가능.

NO / 403

축소 모드로 계속한다. 프로젝트 문서만 읽고 발굴·분석까지만 수행, 프로토 제작은 건너뛴다. 아침 보고 맨 위에 “repo 접근 실패”를 크게 남긴다. 조용히 죽지 않는 것이 규칙.

이 분기가 필요한 이유: 예약 세션이 repo 권한을 물려받는지 아직 실측하지 못했다. 확인 전까지는 실패를 전제로 설계한다.
STAGE 1

발굴 — 두 사냥터 교차

두 줄기를 동시에 훑고, 세 번째로 둘을 교차시킨다.

A) itch.io HTML5 tag: incremental / idle / clicker B) Steam 신작 최근 90일 · 캐주얼 · 아이들 · 정리 C) 교차 역추적 Steam 히트 → itch HTML5 데모 있나? Scritchy Scratchy · Hole Is Mine 이 정확히 이 패턴이었다 ────────────────────────── 출력: 원시 후보 12 ~ 20개
C가 가장 값진 줄기다. 스팀에서 시장 검증이 끝난 게임 중 itch에 웹 데모가 있는 것 — 이게 “검증됐고 + 만져볼 수 있고 + 우리 산출물과 형식이 같은” 삼중 적중이다. 실측한 itch 인크리멘탈 목록 36개 안에 이미 이런 게 섞여 있었다.

신규 후보로 통과.

STAGE 3 · 하드 게이트

시장이 검증했는가?

점수를 매기기 전에 통과/탈락만 가른다. 여기서 떨어지면 분석 비용을 쓰지 않는다.

G1 시장 검증 Steam 리뷰 ≥ 500 · 긍정 ≥ 85% 또는 itch 평점·댓글이 살아있음 G2 규모 2~5인 팀 범위인가 (대형사 배제) G3 리스크 도박 · IP · 심사 → 플래그 G4 충돌 개발사가 이미 모바일로 내려오나
통과

채점 단계로.

탈락

버리지 않고 기록한다. seen.jsonl에 사유와 함께 남긴다 — “리뷰 부족 / 대형사 / 개발사 모바일 진출”. 이 기록이 없으면 내일 밤 또 발굴한다.

G3는 탈락 조건이 아니라 플래그다. 도박 소재는 즉사 조건이지만 “먼저 처리해야 할 항목”으로 다룰 수 있다 — 통화 표기 치환, 실제 브랜드 연상 제거 등. 무조건 버리면 좋은 후보를 놓친다. G4는 실제로 한 번 걸러낸 축이다.
STAGE 4

채점 — 3축 가중 점수표

형님이 고른 세 축. 각 항목 0–5점.

축묻는 것가중
콘텐츠가 숫자인가아트를 더 안 만들고 분량을 늘릴 수 있나×3
자동화가 코어를 돕는가아이들화하면 판타지가 완성되나 파괴되나×3
터치 우위 조작모바일이 마우스보다 나아지는 조작인가×2
보조 — 세션 길이아무 데서나 끊어도 손실 0인가×1
보조 — 리텐션 구조프레스티지가 있나, 엔딩으로 끝나나×1
보조 — 프로토 공수하루 안에 코어 검증이 되나×1
정렬 후 상위 3개만 통과 · 나머지는 보류로 기록
×3 두 축이 사실상 결과를 지배하도록 일부러 벌려놨다. 이 둘은 이미 A/B 리포트에서 실제로 승부를 갈랐던 축이다 — “콘텐츠가 숫자냐 규칙이냐”가 공수 3~5배 차이를 만들었고, “자동화가 코어를 죽이냐”가 정리 게임을 탈락시켰다. 검증된 판별식이라서 가중치를 높게 준다.
STAGE 5

심층 분석 — 상위 3개 각각

읽는 것 긍정 리뷰 + 부정 리뷰 · 데브로그 패치노트 · 태그 · 실적 목록 배제 SEO 자동생성 위키 — 내용을 창작한다 (실측 확인) 신뢰 등급 A 1차 소스 · B 독립 2개 교차 C 단일 출처 (수치는 A만 신뢰) ────────────────────────── 산출 코어 루프 분해 훔칠 것 딱 1개 · 버릴 것 재확인 시점 (예: 출시 60일 리뷰)
부정 리뷰를 반드시 같이 읽는다. 실제로 가장 값진 발견이 거기서 나왔다 — “클리어 후 재플레이 안 함”이라는 한 줄이 리텐션 구조의 치명적 결함을 드러냈고, 그게 후보 하나를 탈락시켰다. 긍정 리뷰만 읽으면 왜 베끼면 안 되는지를 영원히 모른다.
STAGE 6 · 갈림길

PC가 살아있는가?

루프 전체에서 유일하게 외부 조건에 의존하는 지점.

살아있음

크롬으로 itch HTML5 데모를 실제로 플레이 → 스크린샷 → 게임필·아트 관찰 → 점수 보정. 텍스트로는 절대 알 수 없는 “손맛”이 여기서만 들어온다.

꺼짐 · 앱 닫힘

play-pending 큐에 넣고 그대로 진행한다. 텍스트 점수로 프로토를 만들고, 산출물에 “미검증” 딱지를 붙인다. 그날 밤 작업은 실패하지 않는다.

폴백을 이렇게 잡은 이유: PC 의존을 필수로 만들면 PC가 꺼진 날은 밤 전체가 통째로 날아간다. 무인 자동화에서 단일 실패점을 필수 경로에 두면 안 된다. 대신 “아직 안 만져봤음”이 명시적 상태로 남아서, 나중에 반드시 검증받는다.

STAGE 8 · 무인 품질 게이트

게임필 자동 채점 — 사람 눈이 없어도 통과 못 하면 못 나간다

헤드리스 브라우저가 혼자 한 판을 플레이하고, 연출 8종이 각각 몇 번 호출됐는지 센다.

필수 8 트윈 · 오버슈트 팝 · 카운트업 히트스톱 · 셰이크 · 파티클 플로팅텍스트 · 눌림반응 판정 하나라도 0회 → exit code 1
PASS

통과. 커밋 단계로.

FAIL

1회 자동 재시도. 그래도 실패하면 버리지 않고 audit-failed 상태로 커밋하고 아침 보고에 명시한다. 실패를 숨기면 다음 밤에 같은 실패가 반복된다.

이게 이 설계에서 가장 중요한 장치다. 무인 자동화의 진짜 위험은 실패가 아니라 그럴듯한 쓰레기가 조용히 쌓이는 것이다. 그래서 품질 판정을 사람 눈에서 프로그램 종료 코드로 옮겼다.

HTML 프로토가 “웹페이지처럼” 보이는 원인 다섯 중 제일 큰 게 상태가 트윈 없이 즉시 점프하는 것이다. 이모지를 쓰는 것보다 이게 더 치명적이다. 같은 게임 코드로 실측했을 때 게임필 미적용 0/100 → 적용 100/100 이었다.

남은 구멍: 정지 화면의 아트 품질. 클라우드에서 이미지를 못 보므로 여기는 아직 사람 눈이 필요하다. 파이프라인의 마지막 미구현 조각.
STAGE 9 · 산출

커밋 · 푸시 · 아침 보고

nights/2026-08-21/ report.md 아침 보고 1장 candidates.json 발굴·채점 원본 proto-a.html proto-b.html registry/seen.jsonl append only docs/index.html Pages 링크 갱신 ────────────────────────── git commit && git push
seen.jsonl 을 “뒤에만 붙이는” 형식으로 잡은 건 의도적이다. 마크다운 표를 매일 밤 다시 쓰게 하면 세션이 기존 줄을 뭉개거나 충돌을 낼 수 있다. 뒤에만 붙이는 형식은 그 사고가 구조적으로 불가능하다. 사람이 읽는 표는 거기서 매일 새로 뽑아낸다.

Pages 가 이 구조의 숨은 이득이다. 프로토가 단일 HTML이므로 push만 하면 URL이 생긴다 → 아침에 폰에서 링크 눌러 바로 플레이. 파일 받고 열 필요가 없다.

프로젝트 문서

형님이 모바일에서 읽는 판단 기록
  • 주간 요약 · 결정 기록
  • A/B 리포트 같은 사람용 판단 자료
  • repo 접근 실패 시의 폴백 기억
이미 48개 문서가 쌓여 있다. 코드와 상태는 GitHub로 옮기고, 여기는 “왜 그렇게 결정했는가”만 남긴다. 중복 관리하면 반드시 어긋난다.

정직하게 · 아직 안 풀린 것

① 리뷰 병목이 가장 크다

밤에 2~3개면 한 달 60~90개. 만드는 쪽은 자동인데 판정하는 쪽은 형님 한 명이다. 미검토 프로토가 쌓이면 자산이 아니라 부채다. 2주 뒤 밀리는 게 보이면 밤 1개로 줄이는 것을 미리 합의해두고 싶다.

② 예약 세션의 repo 권한 — 미실측

새벽 세션이 이 환경의 허용 목록을 물려받는지 확인하지 못했다. 등록 직후 예약작업을 즉시 한 번 실행해서 push가 되는지 봐야 한다. 추측으로 넘기면 안 되는 지점이라 STAGE 0에 분기를 넣어뒀다.

③ 아트 심사는 여전히 사람 눈

클라우드에서 이미지를 못 본다. 게임필은 종료 코드로 닫혔지만 정지 화면의 아트 품질은 자동 판정이 불가능하다. 파이프라인의 마지막 미구현 조각이고, 이게 닫히기 전까지 완전 무인은 아니다.
