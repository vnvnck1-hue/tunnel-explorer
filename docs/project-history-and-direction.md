## 3. 프로젝트를 관통한 개발 기조

### 3.1 플레이 가능한 검증물이 문서와 함께 간다

GDD는 “전체 방향 고정 → 코어루프 데모로 재미 검증 → 본편 확장”을 목적으로 선언한다. 실제 커밋도 문서, 데모, 자산과 런타임 구현이 짧은 간격으로 함께 움직였다. 아이디어를 오래 추상화하기보다 **브라우저에서 바로 만져 볼 수 있는 상태로 만든 뒤 판단하는 방식**이 반복됐다.

### 3.2 코어루프가 기술이나 콘텐츠 양보다 우선한다

초기 성공 기준은 “한 판 더”가 나오는가였고, 본편 기능보다 역할 선택·목표·탈출·결과의 감각을 먼저 검증하도록 범위를 제한했다. Unity 등 본편 엔진 이전도 코어루프 검증 이후의 일로 남겼다. 저장소가 큰 단일 HTML 빌드를 중심으로 발전한 이유도 이 우선순위와 연결된다.

### 3.3 협동 판타지와 솔로 완결성을 동시에 추구한다

4역할 상호의존과 LAN 코옵은 프로젝트 초기에 이미 핵심이었다. 그러나 솔로 드론에서 AI 크루로 보조 체계를 발전시키고, 개인 경험치와 역할별 행동 가중치를 도입해 한 역할이 노동을 독점하지 않도록 했다. **함께하면 역할 차이가 살아나지만 혼자여도 게임이 성립해야 한다**는 균형이 유지됐다.

### 3.4 보상은 반드시 위험·귀환과 연결한다

보스를 쓰러뜨렸다는 사실보다 살아서 돌아오는 것을 완결로 본다. 코어와 유물은 생환해야 장기 성장으로 전환되고, 탈출 대기·배당·니어미스는 “지금 떠날 것인가, 더 욕심낼 것인가”를 묻는다. 이는 프로젝트의 독특한 감정선을 **발견의 기쁨 → 욕심 → 압박 → 안도 또는 후회**로 만든다.

### 3.5 런 성장과 영구 성장을 분리하되 서로 연결한다

특성 카드는 원정 안의 즉흥적 빌드를, 기지 노드는 장기 목표와 직업 판타지를 담당한다. 런 중 영구 노드를 사던 초기 구조는 두 시간축을 흐린다고 판단해 폐기됐다. 기능을 추가한 뒤에도 상위 설계와 맞지 않으면 되돌리는 **구조적 일관성 우선**의 사례다.

### 3.6 짧은 사이클, 계측, 명시적 미결정 사항을 선호한다

커밋은 기능 단위로 잘게 나뉘고, 누적 기획서에는 `확정`, `구현 완료`, `검증 필요`, `미결정` 상태가 구분돼 있다. 경험치 출처와 비율, 성장 상한, 시뮬레이션 목표 레벨, 예외 상황을 수치 또는 코드 근거로 남겼다. 시간 부족으로 실플레이 계측을 못 한 경우에도 이를 완료로 포장하지 않고 질문 대기 목록에 이월했다.

### 3.7 기능 이후에는 감각 품질을 반복해서 끌어올린다

조명, 방향 스프라이트, 보스 애니메이션, 드릴 사운드, UI 레이아웃, 키아트와 로딩 화면이 여러 차례 갱신됐다. 이는 시각·청각 요소를 마지막 장식으로 보지 않고 **행동의 손맛과 정보 전달을 검증하는 일부**로 다뤘다는 뜻이다.

## 4. 개발 방식에서 드러난 특징

### 강점

- **매우 빠른 학습 속도:** 첫날에 GDD와 플레이 데모를 만들고 열흘 안에 성장·AI·유물·UI·사운드까지 연결했다.
- **설계와 구현의 왕복:** 문서가 단순 희망 목록이 아니라 구현 결과, 폐기 이유, 다음 검증 질문을 누적한다.
- **명확한 중심 감정:** 채굴 자체보다 욕심을 내고도 살아 돌아올 수 있는가에 초점을 맞춘다.
- **역할 판타지 보호:** 모두가 기본 행동은 가능하지만 전문 역할의 고점과 기여 방식은 다르게 설계한다.
- **작은 수직 슬라이스:** 기능을 별도 빌드나 작은 커밋으로 실험한 뒤 통합한다.

### 축적된 기술·운영 부채

- 단일 HTML 빌드가 17MB 안팎까지 커져 코드 탐색, 충돌 해결, 자동 테스트와 모듈화가 어려워질 가능성이 크다.
- 짧은 기간에 버전 파일과 백업이 다수 누적돼 무엇이 본선인지 혼동될 수 있다. 실제 작업일지에도 본선 판정 질문이 남아 있다.
- 자산이 저장소에 대량 포함되어 커밋 규모가 매우 크고, 코드 변화와 자산 동기화가 같은 커밋에 섞인 경우가 있다.
- 일부 밸런스는 코드·시뮬레이션 검증까지 진행됐지만 전체 원정 실플레이 계측은 이월된 상태다.
- 라이선스와 재배포 정책은 README에서 아직 추후 정리 항목으로 남아 있다.

이 항목들은 현재 방향이 잘못됐다는 뜻이 아니라, **프로토타입의 속도를 제품 개발의 지속 가능성으로 전환할 시점에 생기는 자연스러운 과제**다.

## 5. 현재 프로젝트의 정체성

2026년 9월 2일 Git 기록을 기준으로 땅굴 크루는 다음과 같이 정의할 수 있다.

> 4개의 역할을 가진 크루가 절차적으로 이어지는 지층을 채굴·탐사·방어하며 성장하고, 행성 중심부의 보스를 쓰러뜨린 뒤 전리품을 지키기 위해 탈출하는 탑다운 2D 원정형 액션 게임 프로토타입.

제품 방향의 핵심 축은 네 가지다.

1. **역할:** 같은 땅굴에서도 직업마다 가치 있는 행동과 성장 경로가 다르다.
2. **발견:** 지형, 광맥, 유물, 빌드와 보스 전조가 다음 행동을 유도한다.
3. **욕심과 생환:** 더 얻을 기회는 더 잃을 위험과 함께 온다.
4. **누적 성장:** 한 원정의 즉흥적 빌드와 여러 원정에 걸친 장기 성장이 맞물린다.

최근 작업은 이 뼈대를 바꾸기보다 UI, 순간 피드백, 사운드와 연출을 통해 각 축을 더 잘 느끼게 만드는 방향이다.
