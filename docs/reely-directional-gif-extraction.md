## 0. 최초 8방향 GIF 분석과 작업 결정

입력 GIF는 한 프레임 안에 8방향 캐릭터가 3×3 배치로 들어 있는 480×480 스프라이트 보드다.

```text
NW   N   NE
 W       E
SW   S   SE
```

각 프레임에는 같은 8방향 배치가 반복되고, 전체 GIF는 37프레임·프레임당 100ms다. 체크무늬는 GIF의 실제 RGB 픽셀이므로 투명 배경으로 간주하지 않고 연결된 외곽 배경부터 제거했다. 원본 SHA-256은 `4056e2c6101222f282cb2fa414fcd8a4ffd5364f25e05232669b64cbca5c9d5d`로 고정했다.

처음에는 8개 방향을 각각 GIF로 분리하는 방안을 검토했지만, 좌우 캐릭터가 픽셀 대칭에 가까워 게임에서는 좌측 5방향(`SW/W/NW/N/S`)만 원본으로 보존하고 우측 3방향을 수평 플립하는 방식으로 결정했다. 이 방식은 산출물 수를 줄이면서도 좌우 피벗을 동일하게 유지한다. GIF는 피벗과 동작 확인용, 게임 적용은 고정 셀 PNG/스프라이트 시트를 사용한다.

- 투명 인덱스: 0
- disposal: 2
- optimize: false
- 프레임 지속 시간: 원본의 100ms 배열 유지
- 반복: 원본의 `loop=0` 유지

## 9. 작업 방식 메모

생성형 이미지 모델은 사용하지 않았다. 이 작업은 캐릭터의 픽셀과 피벗을 유지해야 하므로, 프롬프트 기반 재생성 대신 원본 GIF에 대한 결정적(deterministic) 픽셀 처리를 사용했다.

### 9.1 GIF 검수와 게임 런타임 자산을 분리한 이유

GIF는 한 파일로 방향별 동작과 피벗을 빠르게 확인하기 좋지만, 게임 런타임에서는 GIF 디코더·팔레트·프레임 접근 시점에 의존하게 된다. 따라서 최종 게임 자산은 동일한 픽셀을 가진 RGBA PNG 프레임과 고정 크기 스프라이트 시트로 만들었다. GIF와 PNG는 같은 추출 결과를 사용하므로 검수 화면과 실제 게임 프레임의 피벗 기준이 달라지지 않는다.

## 10. 5방향 게임용 파이프라인 확장

### 10.1 현재 최종 산출물

GIF는 피벗과 프레임 전환을 빠르게 보는 검수용으로 두고, 게임의 원본 자산은 RGBA PNG 프레임과 스프라이트 시트로 구성했다.

- 공통 루트: `assets/characters/reely-driller-directional/`
- 애니메이션 매니페스트: `assets/characters/reely-driller-directional/animation.json`
- PNG 프레임: `assets/characters/reely-driller-directional/frames/{direction}/frame_000.png` ∼ `frame_036.png`
- 방향별 시트: `assets/characters/reely-driller-directional/sheets/reely-driller-{direction}.png`
- 검수용 GIF: `assets/characters/reely-driller-{direction}-transparent.gif`
- 방향별 검증 JSON: `assets/characters/reely-driller-{direction}-transparent.report.json`

생성한 원본 방향은 `sw`, `w`, `nw`, `n`, `s`다. 오른쪽 방향은 런타임에서 다음과 같이 수평 플립한다.

| 필요 방향 | 원본 방향 | 처리 |
|---|---|---|
| SE | SW | `flipX: true` |
| E | W | `flipX: true` |
| NE | NW | `flipX: true` |
| N | N | 플립 없음 |
| S | S | 플립 없음 |

피벗 X가 셀 정중앙인 112이므로 수평 플립 후에도 피벗은 `(112, 166)`을 그대로 사용한다.

N 방향의 15–22프레임에서는 메인 드릴과 오른쪽 이웃 캐릭터가 실제 픽셀로 맞닿아 하나의 연결 성분이 된다. 따라서 단순 연결 성분 필터 이전에 N 방향 소유 영역 `(0, 0, 184, 224)`를 적용했다. 여러 경계 후보를 시각적으로 비교하여 메인 드릴의 검은 외곽은 남고 이어지는 이웃 캐릭터의 초록색 다리부터 제거되는 `x=184`를 선택했다.

### 10.4 피벗 정책

공통 피벗 `(112, 166)`은 224×224 셀의 수평 중앙과 기준 프레임의 발 아래 지면선을 기준으로 설정했다. 각 방향은 기준 프레임의 발 하단이 약 `y=158`에 오도록 고정 크롭을 배치했고, 피벗은 그보다 8픽셀 아래에 둔다.

게임 렌더러는 프레임의 불투명 외곽 중심을 매번 다시 구하지 않고, 반드시 매니페스트의 고정 피벗을 사용한다.

```js
const drawX = worldX - 112;
const drawY = worldY - 166;
```

시트에서는 해당 셀을 선택하고 `drawX`, `drawY`에 224×224 크기로 그린다. 오른쪽 방향은 월드 피벗 `(worldX, worldY)`를 기준으로 수평 반전한다.

## 11. 액션 분리 및 외곽 반점 정리

### 11.1 행동 구간 분리

원본 37프레임을 추적한 결과, 프레임 0–13은 자연스럽게 이어지는 걷기 블록이고, 14–24는 누움과 복귀를 포함한 넘어짐 블록이다. 25–36은 걷기가 다시 반복되는 구간이므로 제거했다.

| 클립 | 원본 프레임 | 프레임 수 | 재생 | 시트 |
|---|---:|---:|---|---|
| walk | 0–13 | 14 | 반복 | 8열 × 2행, 1792×448 |
| fall | 14–24 | 11 | 한 번 실행 | 8열 × 2행, 1792×448 |

각 방향×액션에 대해 다음 산출물을 생성했다.

- GIF: `assets/characters/reely-driller-actions/gifs/reely-driller-{direction}-{action}.gif`
- PNG: `assets/characters/reely-driller-actions/frames/{direction}/{action}/frame_000.png`
- 시트: `assets/characters/reely-driller-actions/sheets/reely-driller-{direction}-{action}.png`
- 검증: `assets/characters/reely-driller-actions/reports/reely-driller-{direction}-{action}.report.json`

`animation.json` 의 `actions.walk`/`actions.fall` 필드에 위 프레임 범위와 파일 경로를 기록했다. 게임 렌더러에서는 `walk.loop=true`, `fall.loop=false`로 처리한다. 검수용 fall GIF 파일은 반복 표시가 필요할 수 있으므로 원본 GIF와 같이 무한 반복 인코딩하고, 실제 게임 클립에서만 한 번 재생한다.

### 11.2 외곽 반점 제거

기존 배경 제거 후 남은 작은 회색/흰색 성분을 프레임별로 추가 검사했다.

1. 투명 전경 중 밝기 130 이상, 채도 차이 40 이하인 작은 성분을 찾았다.
2. 성분이 캐릭터의 색상/외곽 핵심에 최대 1픽셀만 접하고, 세 방향 이상으로 연결되지 않은 작은 성분은 배경 반점으로 판정해 삭제했다.
3. 코어에 둘러싸인 렌즈/금속 하이라이트는 모서리 접촉 조건이 달라 보존했다.

## 12. 게임 거너 적용

### 12.1 적용 파일과 렌더링 경로

최신 게임 파일 `tunnel-crew-infinite-mode-v7.7.3-ui-develop.html`의 플레이어 렌더링 경로에 거너 스프라이트를 연결했다. 기존 `drawShelly()` 호출은 유지하고, `INF.roleId==='gunner'`일 때만 새 `drawGunnerSprite()`가 우선 실행된다. 시트가 아직 로드되지 않았거나 파일을 찾지 못한 경우에는 기존 벡터 캐릭터가 임시로 표시되어 로딩 중 플레이어가 사라지지 않는다.

렌더러가 읽는 파일은 `assets/characters/reely-driller-actions/sheets/` 아래의 10개 PNG 시트다. `sw`, `w`, `nw`, `n`, `s`를 원본으로 사용하며, `se`, `e`, `ne`는 각각 `sw`, `w`, `nw` 시트를 수평 반전한다.

### 12.2 피벗 고정과 재생 규칙

각 시트 셀은 224×224이고 피벗은 `(112,166)`이다. 기존 게임의 `R_SHELLY` 벡터 실루엣 기준으로 맞춘 뒤, 추가 요청에 따라 셀 표시 높이를 `4.25r`에서 `5.525r`로 30% 확대했다. 게임의 `G.sh.y`는 몸통 중심 좌표이므로 셀 피벗은 기존 벡터 캐릭터의 발바닥 위치인 `(x,y+r)`에 매핑한다. 따라서 프레임별 외곽 크기 변화가 있어도 크기만 커지고 발 위치는 흔들리지 않는다.

```js
const scale = (r * 5.525) / 224;
const drawX = -r * 5.525 / 2;
const drawY = r - 166 * scale;
```

- 이동 중: `walk` 14장을 10fps로 반복한다.
- 정지 중: `walk`의 0번 프레임을 유지한다.
- `G.downed===true`: `fall` 11장을 10fps로 한 번 재생하고 마지막 프레임에서 정지한다. `G.downT`가 재생 시간을 제공하므로 다운 진입 시점부터 동일하게 시작한다.
- 기존 게임의 조준 각도(동쪽 0라디안 기준)를 8방향으로 양자화하고, 우측 3방향은 피벗을 기준으로 반전한다.

AI 크루를 관전하거나 함께 플레이하는 경우에도 `roleId==='gunner'`인 AI에 같은 시트를 적용한다. AI의 `m.downT`를 사용해 다운 동작을 시작 프레임부터 재생하고, 다른 역할의 AI 렌더링에는 영향을 주지 않는다.

### 12.3 정적 검증

인라인 메인 스크립트 전체를 `new Function()`으로 구문 검사해 통과했다. 게임 코드가 참조하는 10개 시트 파일의 경로와 파일 존재를 확인했으며, 각 시트는 액션 분리 단계의 224×224 고정 피벗 결과물이다. `fall`은 게임 상태에서만 비반복으로 재생하고, 검수용 GIF의 반복 여부와 분리했다.

## 13. 다른 에이전트(예: Claude)로 재현할 수 있는가

이 작업은 GPT 전용 프로세스가 아니다. 핵심 산출물은 모델이 새로 그린 이미지가 아니라 `extract_directional_character_gif.py`가 수행하는 결정적 픽셀 처리 결과이므로, Claude 에이전트도 같은 파일과 명령을 실행하면 동일한 결과를 만들 수 있다.

### 13.1 동일 결과를 보장하는 조건

- 동일한 입력 GIF SHA-256
- 동일한 추출 스크립트 버전
- 문서에 기록된 크롭·시드·소유 영역·피벗 파라미터
- 동일한 액션 범위(걷기 `0–13`, 넘어짐 `14–24`)
- GIF/PNG/시트의 검증 보고서가 0 불일치인지 확인

이 조건을 지키면 Claude, GPT, 또는 일반 Python 실행 환경 모두 픽셀 단위로 같은 결과를 낸다. 반대로 에이전트가 문서의 설명만 보고 크롭 경계나 배경 판정 규칙을 다시 추정하면, 모델 종류와 무관하게 결과가 달라질 수 있다.

### 13.2 게임 통합에서 달라질 수 있는 부분

게임 HTML의 버전이 바뀌었거나 렌더러 구조가 달라지면 스프라이트 경로·스케일·월드 피벗 연결부를 새로 확인해야 한다. 현재 문서에는 최신 게임 파일의 적용 위치, `5.525r` 표시 배율, `y+r` 발바닥 매핑, 걷기/다운 상태 규칙을 기록했으므로 같은 파일에 패치를 적용할 때는 재현 가능성이 높다. 다른 게임 버전에 적용할 때는 파일 구조를 먼저 검사한 뒤 동일한 수치와 검증 절차를 이식해야 한다.

### 13.3 Claude 에이전트 작업 전 체크리스트

Claude에게 작업을 맡길 때는 다음 순서를 그대로 전달한다.

1. **작업 범위 확인:** 이 문서와 프로젝트의 `AGENTS.md`를 먼저 읽고, 사용자가 지정한 단일 게임 파일만 수정한다. 임의의 `v2`, `backup`, `final2` 파일을 만들거나 기존 사용자 변경을 되돌리지 않는다.
2. **원본 확인:** 입력 GIF가 `C:\Users\Loadcomplete\Downloads\reely-studio-260901-7699.gif`인지 확인하고 SHA-256이 `4056e2c6101222f282cb2fa414fcd8a4ffd5364f25e05232669b64cbca5c9d5d`인지 검사한다. 해시가 다르면 기존 결과를 덮어쓰지 말고 먼저 사용자에게 알린다.
3. **결정적 스크립트 사용:** 이미지 생성 모델, 자동 리드로잉, 색상 보정, 프레임별 자동 중앙 정렬을 사용하지 않는다. `tools/extract_directional_character_gif.py`와 이 문서의 고정 파라미터를 사용한다.
4. **파라미터 고정:** 방향별 크롭, N 방향 소유 영역 `(0,0,184,224)`, 시드, 공통 피벗 `(112,166)`, 액션 범위 `walk=0–13`, `fall=14–24`를 임의로 바꾸지 않는다.
5. **플립 규칙 준수:** 우측 방향은 새로 추출하거나 다시 그리지 않고 `SE←SW`, `E←W`, `NE←NW` 수평 플립으로 처리한다. 플립 중심은 셀 중앙과 고정 피벗을 기준으로 한다.
6. **배경 제거 주의:** 캐릭터 내부의 고글·금속 하이라이트를 배경으로 삭제하지 않는다. 크롭 가장자리의 이웃 캐릭터 조각과 외곽 회색/흰색 반점만 제거한다.
7. **런타임 자산 구분:** GIF는 검수용으로 유지하고, 게임에는 224×224 RGBA PNG 프레임/시트를 연결한다. GIF를 게임에서 직접 디코딩하는 방식으로 바꾸지 않는다.
8. **게임 코드 확인:** 적용 전에 최신 HTML의 `drawShelly`, 거너·엔지니어·스카우트·드릴러 역할 판정, `G.downed`/`downT`, AI의 `m.down`/`m.downT` 경로를 확인한다. 다른 역할의 AI 렌더링이나 기존 게임 로직을 변경하지 않는다.
9. **피벗·크기 보존:** 현재 게임 배율 `5.525r`와 게임 바닥선 `(x,y+r)` 매핑을 유지한다. 역할별 피벗은 이 문서 17.3 표를 사용하고, 프레임별 바운딩 박스를 다시 계산해 위치를 보정하지 않는다.
10. **검증 후 보고:** 메인 스크립트 구문 검사, 10개 시트 파일 존재/HTTP 응답, GIF·PNG·시트 프레임 수, 투명 마스크/RGB 불일치, 캔버스 경계 접촉을 확인한 뒤 결과 파일과 실패 항목을 보고한다.

### 13.4 Claude 작업에서 피해야 할 판단

- “더 자연스럽게 보이게” 하기 위해 캐릭터를 다시 그리거나 AI 이미지 생성으로 대체하지 않는다.
- 프레임마다 캐릭터 중심을 새로 계산해 흔들림을 보정하지 않는다. 이 프로젝트의 목적은 이미 맞춰진 원본 피벗을 보존하는 것이다.
- GIF의 체크무늬를 투명 정보로 오해하지 않는다. 실제 RGB 배경이며, 외곽 연결성으로 제거해야 한다.
- N 방향 이웃 픽셀을 단순 연결 성분만으로 남기지 않는다. 기록된 소유 영역을 먼저 적용한다.
- 기존 HTML이 최신이라는 가정만으로 바로 덮어쓰지 않는다. 파일명·수정 시각·렌더 함수가 문서와 일치하는지 먼저 확인한다.
- 검증 실패를 “시각적으로 괜찮다”는 이유로 무시하지 않는다. 불일치가 있으면 원인과 영향을 기록하고 사용자 확인을 받는다.

## 17. 최종 프로세스 감사: 피벗·크기·비교 기준

### 17.1 전체 처리 순서

모든 캐릭터는 다음 동일 순서를 따랐다.

1. 480×480 원본 GIF의 3×3 방향 배치, 37프레임, 100ms, RGB 체크무늬 배경을 확인한다.
2. 좌측 5방향만 224×224 고정 셀로 크롭하고, 시드·소유 영역으로 메인 캐릭터만 보존한다.
3. 외곽 체크무늬·중성색 반점·크롭 가장자리 이웃 캐릭터를 연결성 기준으로 제거한다. 캐릭터 내부 하이라이트는 제거하지 않는다.
4. 원본 프레임 `0–10`을 walk 11장, `11–26`을 fall 16장으로 분리하고 `27–36`의 중복 걷기를 버린다.
5. GIF는 검수용으로 유지하고, 게임에는 동일 픽셀의 224×224 RGBA PNG 시트를 연결한다.
6. 동쪽 기준 조준각을 8방향으로 양자화하고 `SE←SW`, `E←W`, `NE←NW`로 수평 플립한다.
7. 플레이어와 AI의 동일 역할 렌더 경로에 시트를 연결하고, 시트 로드 실패 시 기존 렌더를 임시 폴백으로 사용한다.

### 17.2 크기 비교와 30% 확대가 들어간 방식

초기 게임 연결에서는 새 시트의 표시 높이를 `4.25r`로 잡았다. 실제 게임 화면에서 기존 `drawShellyVector()`의 몸통·그림자·발바닥 기준 및 역할 선택 카드의 기존 캐릭터 실루엣(`assets/characters/{driller,gunner,scout,engineer}-playable.png`)과 나란히 비교한 결과, 새 캐릭터가 작게 보였다. 이에 표시 높이를 `4.25r × 1.30 = 5.525r`로 통일했다.

게임의 기준 반지름은 `R_SHELLY=25`이다. 따라서 초기 셀 표시 높이는 `106.25` 월드 픽셀(`4.25×25`)이었고, 현재는 `138.125` 월드 픽셀(`5.525×25`)이다. 역할 선택용 기존 아트는 모두 500×500 캔버스이며, 원본 캔버스 여백이 달라 단순 캔버스 크기가 아니라 보이는 실루엣과 발바닥선을 비교 기준으로 삼았다.

| 기존 역할 아트 | 캔버스 | 불투명 실루엣 영역(참고) |
|---|---:|---|
| `driller-playable.png` | 500×500 | `(76,30)–(425,470)` |
| `gunner-playable.png` | 500×500 | `(25,7)–(478,494)` |
| `scout-playable.png` | 500×500 | `(76,10)–(425,487)` |
| `engineer-playable.png` | 500×500 | `(74,7)–(444,489)` |

현재 네 렌더러 모두 다음 계산을 사용한다.

```js
const h = r * 5.525;
const scale = h / 224;
const drawX = -h * 0.5;
const drawY = r - pivotY * scale;
```

따라서 224×224 원본 셀의 픽셀은 확대될 뿐 다시 그려지거나 프레임별로 크기가 재계산되지 않는다. 기존 게임의 월드 반지름 `r`, 그림자 기준 `y+r`, 캐릭터 선택 카드의 전체 실루엣 비율을 동시에 기준으로 삼아 역할 간 체감 크기를 맞췄다.

### 17.3 마지막 피벗 엇나감 수정 이력

엔지니어 적용 후 정면(S) 캐릭터가 공중에 떠 보이는 문제가 확인됐다. 원인은 보정 크롭 `(128,278,352,502)`에 대해 사용한 S 피벗 `(112,190)`이 실제 걷기 발바닥 하단 y=153보다 37픽셀 아래에 있었기 때문이다. 그 점을 게임 바닥선에 매핑하면서 발이 위로 떠 보였고, 프레임별 발 하단을 측정해 S 피벗을 `(112,153)`으로 교체했다. 같은 방식으로 엔지니어의 방향별 피벗을 SW 163 / W 179 / NW 182 / N 180 / S 153으로 확정했다.

이후 스카우트와 드릴러에도 동일한 바닥 기준을 적용했다.

| 역할 | SW | W | NW | N | S |
|---|---:|---:|---:|---:|---:|
| 거너 | 166 | 166 | 166 | 166 | 166 |
| 엔지니어 | 163 | 179 | 182 | 180 | 153 |
| 스카우트 | 161 | 158 | 165 | 183 | 164 |
| 드릴러 | 164 | 176 | 178 | 165 | 176 |

각 값은 해당 방향 walk 11프레임의 실제 불투명 하단을 기준으로 한 고정 셀 y좌표다. `drawY = r - pivotY*scale`로 계산해 하단을 게임 바닥선 `(x,y+r)`에 매핑하며, fall 프레임에도 같은 월드 기준을 유지한다. 프레임마다 바운딩 박스를 다시 계산하거나 자동 중앙 정렬하지 않는 것이 피벗 보정의 핵심이다.
