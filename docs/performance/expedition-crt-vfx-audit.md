# CRT → 원정 콘텐츠/VFX 성능 감사

대상 브랜치: `codex/expedition-content-projectile-vfx`
대상: Unity 본편

## 결론

새 콘텐츠의 시뮬레이션 비용은 목표 셀 최대 3개, 계약 상태 1개, 도감 ID 약 30개 수준이라 병목 후보가 아니다. 실제 위험은 CRT의 전체 화면 패스와 전투 VFX의 렌더러·파티클·일시 할당이 동시에 겹치는 경우다. 이번 변경은 신규 VFX를 명시적 예산 안에 넣고, 기존 전투 표현 경로에서 발견된 매 프레임 할당과 수명 누수를 함께 제거한다.

## CRT 비용 경계

- CRT는 현재 프레임의 최종 화면에 전체 해상도 유리 패스 1회를 수행한다.
- 잔광이 켜진 프리셋만 히스토리 복사 패스 1회가 추가된다. 잔광이 꺼지면 히스토리 RT를 즉시 해제한다.
- 히스토리는 1440p까지 원본 해상도, 그보다 큰 화면은 1/2 가로·세로 해상도다.
- 선호 포맷 `B10G11R11_UFloatPack32` 기준 히스토리 메모리는 1080p 약 7.9 MiB, 1440p 약 14.1 MiB, 4K도 다운샘플되어 약 7.9 MiB다. 장치가 소스 포맷으로 폴백하면 런타임 `HistoryBytes` 계측값을 기준으로 본다.
- 감쇠 `pow`는 픽셀 셰이더가 아니라 CPU에서 프레임당 한 번 계산한다.
- `TunnelCrew CRT glass`, `TunnelCrew CRT history copy` GPU 샘플과 Setup/RenderGraph 할당량 계측 지점이 이미 있다.

## 신규 VFX 예산

| 항목 | Low | Medium | High/Ultra | 정책 |
|---|---:|---:|---:|---|
| 표시 투사체 | 64 | 80 | 96 | 가장 최근 탄을 우선 표시, 시뮬레이션 판정은 생략하지 않음 |
| 착탄 파티클 배율 | 50% | 75% | 100% | 최소 1개로 피드백 유지 |
| 절차 충격 도형 | 96 | 96 | 96 | 초과 시 가장 오래된 상태 재사용 |
| Shuriken 최대치 | 1,640 합계 | 1,640 합계 | 1,640 합계 | chunks 420 / burst 560 / spikes 420 / smoke 240; 실제 방출 수만 품질별 축소 |

## 적용한 최적화

- 모든 플레이어 탄은 공용 `Projectile-Energy` 머티리얼 하나를 쓰고 `SpriteRenderer` 풀을 재사용한다.
- 적탄·설치물·보스탄·보조 드릴·임무 마커 렌더에서 프레임마다 만들던 캡처 람다를 제거했다.
- 활성 상태가 실제로 바뀔 때만 `SetActive`를 호출한다.
- 고빈도 착탄 팔레트를 정적 배열로 바꿔 매 착탄 `Color[]` 할당을 제거했다.
- 절차 도형의 상태 객체도 풀링하고 최대 96개에서 재사용한다.
- 파티클·보스 예고선 머티리얼은 공유 참조로 유지하고 컴포넌트 파괴 시 명시적으로 해제한다.
- 도감 조회는 `HashSet`으로 중복 검사하며, 타일 ID 생성과 계약 HUD 문자열은 상태가 변할 때만 갱신한다.

## 검증 기준

- 100개 투사체를 두 프레임 연속 렌더해도 렌더러 수가 96에서 증가하지 않는다.
- 140개 절차 링을 연속 요청해도 활성 도형은 96개다.
- 셰이더는 Unity `ShaderUtil.ShaderHasError` 검사를 통과해야 한다.
- 실제 플레이 프로파일링 때 CRT 계측을 켜고 `SetupAllocationBytes`, `GraphAllocationBytes`, 두 GPU 샘플을 기록한다. 해상도·GPU에 따른 실측값은 정적 분석으로 단정하지 않는다.
